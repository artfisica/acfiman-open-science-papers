\section{Metodología y arquitectura del entorno docente}
\subsection{Separar contenido, entorno y ejecución}
La reconstrucción documental conserva las revisiones fechadas de los repositorios y contrasta el programa público con los materiales. El análisis técnico examina las interfaces entre contenido, entorno y ejecución, contrasta opciones con su documentación oficial y especifica qué registros permitirían evaluar una sesión. La figura~\ref{fig:arquitectura} representa esas interfaces. La arquitectura distingue tres capas. La primera contiene el problema científico: datos de ejemplo, ejercicios, explicaciones y criterios de interpretación. La segunda define el software necesario para trabajar. La tercera ejecuta comprobaciones y produce salidas. Esta separación permite modificar una pregunta sin rediseñar el entorno, o actualizar una dependencia sin reescribir toda la actividad.

Los contenedores de desarrollo describen un entorno mediante archivos versionados; GitHub Codespaces puede utilizarlos para ofrecer un espacio accesible desde el navegador \cite{devcontainers}. Esta descripción debe incluir dependencias y comandos de preparación. El acceso web reduce la necesidad de instalar herramientas científicas en cada equipo, pero sigue requiriendo una cuenta, conectividad y recursos disponibles. Un entorno descrito no es necesariamente inmutable: imágenes etiquetadas y paquetes sin fijar pueden cambiar entre ejecuciones.

Los repositorios docentes \texttt{jupyter-on-codespaces} y \texttt{exercises-silafae} proporcionan ejemplos públicos del enfoque, citados mediante revisiones de noviembre de 2024 \cite{repos}. Para una sesión, la unidad que se debe conservar es una revisión concreta del repositorio junto con la imagen del entorno y la versión del conjunto de datos. Así se distingue el material impartido de las actualizaciones posteriores. El mismo patrón admite la escala de una tesis: el depósito en Zenodo de un análisis de licenciatura defendido en 2022 conserva código derivado del marco C++ de ATLAS Open Data bajo su licencia original, identificadores de los conjuntos de datos y una ruta de ejecución desde Codespaces o desde una máquina virtual preparada para trabajar sin conectividad \cite{tesisaltuve}.

\subsection{Git y automatización como herramientas de razonamiento}
Git registra cambios en los materiales y permite relacionar una decisión con una revisión concreta. En una actividad de física, un cambio puede afectar la selección de eventos, una normalización o una figura. El estudiante debería poder explicar qué modificó y por qué, además de obtener una salida. El historial ayuda a revisar esas decisiones, aunque no sustituye la explicación científica.

La automatización ejecuta tareas previamente definidas. Un flujo puede comprobar que un cuaderno corre desde un estado limpio o generar una figura con parámetros conocidos. Una configuración de integración continua complementa el entorno interactivo al ejecutar el mismo comando de validación sobre las fuentes versionadas. La migración a otro servicio debe probar ese comando y adaptar autenticación, almacenamiento y configuración del ejecutor.

\subsection{Una práctica de física que se pueda inspeccionar}
Como diseño docente proponemos partir de una distribución física sencilla producida a partir de datos abiertos. Una secuencia puede pedir reproducir la distribución de referencia, variar una selección, comparar el resultado y justificar la diferencia. Deben declararse unidades, muestra utilizada y normalización. Una comprobación automática puede detectar una columna ausente o una ejecución incompleta; no puede establecer por sí sola si una elección física es apropiada.

Conviene conservar una muestra pequeña para comprobar el funcionamiento y separar esa prueba del análisis completo. También debe evitarse que un cuaderno conserve resultados de una ejecución anterior incompatibles con su código actual. Ejecutarlo desde un estado limpio ayuda a detectar dependencias implícitas. El producto evaluable es el análisis acompañado de una explicación de sus decisiones.
